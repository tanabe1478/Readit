# Readit — AIが書いたコードを理解するIDE

## 基本方針

VSCodeやZedと同様の、ファイルツリー、ファイルタブ、コード本文のUIを踏襲する。
既存のリポジトリ構成をそのまま扱い、読むための機能を追加する。
書く機能も残し、「仮説を立ててコードを変え、結果を観察する」を理解の一部として支援する。

読む体験の単位は、将来的にはファイルに加えて「今回のAIの変更」とする。
ユーザーは、変更の意図、関係するコード、期待する挙動、未解決の疑問を往復できる。

## 画面構成

| 場所 | 基本UI | 読むために追加する機能 |
| --- | --- | --- |
| 左 | フォルダを開閉できるファイルツリー | 任意に切り替える読む順番、変更ファイルの表示 |
| 上 | 開いたファイルのタブ、変更状態 | レビュー対象の変更集合・snapshot選択 |
| 中央 | 行番号付きのコード本文と編集 | 差分、関連箇所の抜粋、根拠へのジャンプ |
| 右 | 必要なときに参照する補助パネル | 疑問、説明、根拠、理解済み、未確認の記録 |
| 下 | 実行結果を観察する領域 | 仮説、実験用変更、変更前後のテスト・出力比較 |

ファイルツリーを独自の読む順番で置き換えない。読む順番は別表示として提供する。
中央のコードを主役に保ち、AIの長文説明で画面を埋めない。

## 読むための機能

### 変更の説明と根拠

「割引後の金額で送料を判定するようにした」という説明から、条件分岐、入力型、境界値テストへ移動する。
AIの主張、コードから確認できた事実、テストで観測した結果、未確認を分ける。
説明には対象snapshotと根拠のpath/rangeを要求し、根拠が古くなった説明は再確認対象にする。
要約は短く、詳細は必要な箇所だけ開く。

### 読む順番

変更の入口 → データの契約 → 中心の処理 → 呼び出し元／影響範囲 → 検証の順に案内する。
根拠となるシンボル参照を示し、順番はユーザーが変更できる。
試作の順番はファイル名ヒューリスティックであり、依存グラフやAI分析ではないと明示する。

### 疑問と理解の記録

行・シンボルに「なぜこの値？」「失敗時はどうなる？」を残す。
閲覧しただけでは理解済みにしない。内容が変われば理解済みを引き継がず、関連する記録を再確認対象にする。
将来的に「自分の言葉で説明する」「この入力なら結果は？」を任意で追加する。

### 変更して観察する

変更前に期待する挙動を記録し、独立した作業場所で条件・入力を小さく変える。
同じ入力・コマンド・環境で前後のテスト、出力、実行経路を比較する。
元の作業ツリーへ反映するか破棄するかは分ける。
worktreeは元の変更からの分離に使うが、コード実行のセキュリティサンドボックスとは扱わない。

## 今回の試作と次段階

| 項目 | 状態 |
| --- | --- |
| GPUIネイティブアプリ | 実装 |
| ファイル階層のツリー・タブ・行番号付き本文 | 実装 |
| 読む順番への切替 | ファイル名による仮案内として実装 |
| 差分 | HEAD／起動時の内容との比較を実装 |
| 疑問と理解済みの永続化 | 実装 |
| 根拠を辿る | LSPによる定義・型定義・実装・参照・シンボル・型情報、プレビュー、移動履歴を実装 |
| 編集 | 複数行直接編集、選択、Undo/Redo、コピー／貼り付け、インデント、保存・すべて保存 |
| テスト結果の観察 | ターミナルでの外部実行。統合ランナーは未実装 |
| AI説明・変更集合の読解 | 次段階 |
| 基本IDE操作 | ファイル／フォルダ操作、閉じる確認、タブ復元、クイックオープン、検索・置換、折返し、ショートカット |
| LSP/構文解析 | Tree-sitter色分けとPython／JS・TS／RustのLSP読解機能を実装。補完・診断・renameは次段階 |

Tree-sitterをGPUI Component経由で構文ハイライトに利用している。
これだけで型情報や動的呼び出しの全体が解決するとは扱わず、language serverと組み合わせる。
[Tree-sitter公式](https://tree-sitter.github.io/tree-sitter/)

## 実用版までの順序

1. 基本IDEの読みやすさ: ツリー、タブ、検索、構文色分け、折返し、複数行編集、Undo、日本語入力、キーボード操作。
2. AI変更の読解: 開始snapshotの捕捉、変更集合、根拠付き説明、読む順番、参照先のインライン表示。
3. 観察による理解: worktree上での実験、明示的な実行、前後の結果比較、仮説と結果の記録。
4. 製品化: 大規模repo、アクセシビリティ、更新と署名、依存ライセンス一式、課金。

最初の対象はローカルGitリポジトリを持ち、AIの変更を受け入れる前に理解したい開発者。
AIの出力の出自は、既存差分だけから推測しない。後から使い始めた場合はユーザーが比較範囲を指定する。

## 評価方法

同程度の規模のAI変更を従来IDEとReaditで読んでもらい、次を測る。
「変更の目的を説明できるまでの時間」「影響を受ける呼び出し元を特定できたか」
「境界条件の挙動を予測できたか」「見落とした不具合」「再開時の文脈復帰時間」。
要約を読んだ速さや理解済みボタンの数を、理解の正確さの代用にしない。

非公開アプリのライセンス販売と、任意のAI利用料・チーム共有を分ける構成を候補とする。
価格や市場規模の調査は今回行っていないため、売上や需要は未検証。
